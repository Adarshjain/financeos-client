Section 7

07Client / frontend deep dive

Executive summary

A Next.js 16 App Router application (React 19, TypeScript) that renders every authenticated screen twice on purpose: a Server Component page.tsx makes the first API calls and seeds a per-request TanStack Query cache, then a client component hydrates that cache and owns all later reads and writes through browser fetch. The app began as pure Server Components plus Server Actions (the README still describes that design) and was migrated module by module onto TanStack Query in September 2026 while keeping the RSC first paint. Confirmed

Two API layers are both live: lib/apiClient.ts (server-only, 1,349 lines of per-domain wrappers) for RSC prefetch, and lib/api/client.ts (browser openapi-fetch) for interactivity. Three refresh mechanisms coexist. List filters live in component state, not URLs, except the Activity (job history) page; a few deep-link parameters (?item= on /inbox, ?bill= on /upcoming, ?account= on /transactions/import and /rewards/rules) only select or highlight a row. Chat transcripts live only in React state.

Confirmed

Inbox badge. NavTree and MobileNav both read useInboxSummary() (GET /inbox/summary, polled every 60 s, staleTime 30 s). The badge is summary.badge = act-now rows + needs-a-look rows (info rows never count), rendered by formatBadge as a rose pill, capped at "99+", hidden at 0. Every GET /inbox also writes the summary key, so the badge and the Inbox page agree. The protected layout does not prefetch it; the badge appears after the first client fetch.

Mobile bar. MobileNav is a floating bar (hidden at lg and above, slid away while the on-screen keyboard is open). getMobileNavContext(pathname) picks its items: Home / Inbox / Upcoming / Transactions by default; inside a group (/transactions, /rules, /investments, /loans, /rewards, or /dashboards, /reports, /chat for Insights) it shows that group's short labels plus a left "X" link back to /dashboard. The right end is always the menu button.

Menu sheet. The menu button opens MobileMenuSheet, a bottom-sheet Dialog: a Chat row ("Ask your data"), an Accounts row, the five groups as chip rows (a chip whose label equals its group name reads "All", so Transactions shows All · Review · Rules · Categories · Import), a divider, a Settings chip group (Profile & appearance /settings, Connections /settings/gmail, AI keys /settings/llm-keys, Notifications /settings/notifications, Activity /settings/activity, Debug /debug), then the signed-in email and Sign out. The Settings chips are a local SETTINGS_ITEMS list, kept out of NAV_ITEMS on purpose so they do not affect sidebar prefix highlighting; /settings is active only on itself. Any link closes the sheet. Redirects (server redirect() in the old page files): /settings/ingest → /transactions/import and /settings/jobs → /settings/activity, both keeping the query string; /loans/calendar → /upcoming (query dropped). The Gmail page keeps its /settings/gmail route because the OAuth redirect URI points at it; only its label changed to "Connections".

The mounted NavTree still shows a plain "Needs Review" label with no count. getNavigationTree(needsReviewCount, inboxCount) and AppShellNav.tsx remain dead (zero importers outside each other). What Home is. Home is an ordinary dashboard named "Home" and marked default, seeded once per user. The claim is a conditional UPDATE of users.home_seeded_at (V93), so two concurrent first requests seed once and a failed seed rolls the claim back. The trigger is lazy: the first GET /dashboards or /dashboards/default. The seeded layout on the 100-column grid is Net worth (x 0, w 50) and Inbox (x 50, w 50) on the first row, then Bills due (w 100), Upcoming (w 100, params.days 14) and the "Spend this month" report widget (w 100). That report is a CHART (bar, dimension category, measure spend SUM, filters date this_month, type is DEBIT, isExcluded false, isTransferLeg false); restore reuses an existing report with the same name and datasource instead of creating another. Restore always creates a new Home and makes it the default; an older Home stays as a second dashboard. See M9 · Dashboards.

Built-in widgets. A widget is kind: "report" (has reportId) or kind: "builtin" (builtinKey + optional params). The server's BuiltinWidgetRegistry defines four: net_worth (template KPI, minW 50, Open → /accounts), attention (label "Inbox", component, minW 50, Open → /inbox), upcoming (template TABLE over obligations, minW 100, param days 1..90, Open → /upcoming) and bills_due (component, minW 100, optional accountId param, no Open). A template carries a datasource and report definition run directly by ReportDataService.runDefinition with no report row; a component is drawn by its own client component. The editor lets a built-in be added several times (the Add widget dialog's "Built-in" list, with a params step when needed), resized but never below its minW (validateWidgets and the server's DashboardValidator both check), and removed. In edit mode a built-in gets the title override, the half/full width toggle (disabled when its minW is the whole grid) and Remove, but no edit-report link: there is no report behind it to edit. In view mode Open appears only on built-ins; the overflow menu offers "Edit report" (report widgets), "Duplicate as my report" (template built-ins: copies the template definition with the widget's params into a new saved report via POST /reports) and "View full page".

There is no Bills Due card hard-coded into the page any more; bills reach Home only through the bills_due widget, and the old BillsDueCard is deleted. On a phone the view is DashboardStack: widgets in reading order (layout y, then x), KPIs 140 px tall, charts and tables 320 px, component widgets sized to content. Edit mode keeps the grid. Kinds and keys. One collector per kind: bill (bill:<statementId>; OPEN or PARTIAL due within 7 days as warning, OVERDUE as critical, DUE_UNKNOWN asks for details), emi (emi:<loanId>:<seq>), lending (lending:<counterpartyId>), statement_expected (statement-expected:<accountId>:<periodEnd>, Upload action), gmail_reconnect (gmail-reconnect:<connectionId>), gmail_attention and review (summary rows, needs-a-look), job (job:<jobId>; failed jobs in needs-a-look, finished ones in info), reward_milestone and reward_cap (keyed per window, e.g. reward-cap:<id>:<windowStart>, so the next window is a new row; info section). Listing never calls a producer's evaluate and never advances a notification marker, so opening the Inbox cannot cause or suppress a push.

Snooze and dismiss. Both upsert one inbox_item_state row per (user, key) (V94, unique). Snooze needs a date after today (the client's date dialog enforces min tomorrow; the server returns 400 otherwise) and is refused on summary rows; the row returns on the until date. Dismiss sets dismissed_at and hides the row until the state is cleared; since a bill keeps one key across due-soon and overdue, a dismissed bill stays hidden after it turns overdue. Undo is DELETE /inbox/{key}/state, which forgets both. Keys contain ":"; openapi-fetch percent-encodes the raw key, so the client must not encode it again. Debug · /debug

The diagnostics and debug interface provides real-time LogQL correlation and client-side error inspection:

  • Who sees what: Administrators (every signed-in user while ADMIN_EMAILS is unset; only the listed emails once it is set) see the full reference lookup tool powered by Loki queries, including HTTP request details, root cause analysis with diagnostic hints, interactive timeline entries with expandable stack traces, and on-demand raw log export. Non-administrators see a developer notice ("Send this reference to the developer…") and a local ring buffer of errors without Loki querying capabilities.
  • Client ring buffer: errorLog keeps up to 20 newest errors in localStorage under financeos:diagnostics:errors tagged by ownerUserId. It resets on account change or session expiration. Deduplication logic merges consecutive errors with the same reference and error code occurring within 3 seconds rather than appending redundant rows. Users can copy formatted diagnostic reports, share via Web Share API / clipboard, and clear history.
  • Toast error contract: When an API error occurs, toastError and toastErrorResult record the event in the client ring buffer and show a Sonner error toast displaying Ref <ref> with action buttons: Copy ID (copies reference to clipboard) and Debug (navigates directly to /debug?ref=<encoded>).
  • ErrorState and DiagnosticsProvider: Root error boundaries render ErrorState displaying the page request ID or error digest with Copy ID and Debug links. DiagnosticsProvider wraps the protected layout, injecting pageRequestId from incoming HTTP headers, user admin status, and Faro telemetry sessionId.
