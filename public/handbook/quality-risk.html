Section 22

22Code quality assessment

Executive summary

The codebase is consistent and disciplined in its patterns (layered server, typed client boundary, idempotent migrations, tenancy aspect, exhaustive E2E). Its weaknesses are the ones typical of fast AI-assisted growth: a handful of very large classes, duplicated logic (three sign conventions, two KPI engines, two FY definitions), dead code left after redesigns, stale documentation, and no optimistic locking. Quality is high where a plan document exists and lower where a fix was made in place. Confirmed for all measurements; ratings are the author's judgement.

Strengths

  • Tenancy by construction: @Filter on 34 entities + aspect; native SQL always binds user; chat uses Oracle-side identity. E2E sweeps every endpoint with a foreign id.
  • Money as BigDecimal on the server with explicit scales; DB NUMBER(19,4); client only formats.
  • Typed API boundary: generated schema.d.ts with CI drift gates and a surface checker; openapi-fetch for hooks.
  • Migrations: idempotent PL/SQL from V63, double-boot verified in CI; V79/V82/V85 written with recovery in mind.
  • Consistent module layout: controller → service → repository → entity per domain; DTOs as records; validation via Jakarta annotations.
  • Explicit invariants in plans: rewards, loans, lendings, corporate actions have plan documents that match the code's shape.
  • Observability: request ids end to end, JSON logs with MDC, Faro in the client, structured job results.

Section 23

23Security review

Executive summary

Tenant isolation is the strongest part of the system: three independent mechanisms, exhaustively swept by E2E. Secrets at rest are encrypted with AES-GCM under two master keys. The material findings are one missing OAuth state check (login CSRF), unencrypted statement PDFs kept as job artifacts for up to 7 days, a session cap that never frees slots, a committed session-cookie file, and a set of operational exposures on the single VM.   1. HTTPUserContextFilter resolves the session user into a ThreadLocal; job worker sets it from the job row

  4. ChatCHAT_RO sees only v_chat_* views that filter on SYS_CONTEXT('USERENV','CLIENT_IDENTIFIER'), set per connection
  5. TestE2E foreign-id sweep across 193 operations; "Security Breach Attempt" log on ownership mismatch

Sections 24 and 58

24Performance and scalability

Executive summary

FinanceOS is a compute-on-read system running on a 512 MB heap with two job threads. Every derived number (balance, positions, rewards, schedules) is recomputed per request from full history. This is correct and cheap at personal scale (thousands of transactions) and will degrade linearly with history; nothing is cached server-side. The client side is well tuned (RSC prefetch, 30 s staleTime, server pagination, code-split charts). Confirmed for mechanisms; no load measurements exist in the repository.

Database

  • Pool: Hikari 10 connections; Oracle ADB always-free allows 20 sessions; CHAT_RO uses a separate small pool.
  • Indexes: user_id on every tenant table; (account_id, transaction_date); (account_id, sha256) per statement; job (status, run_after); Gmail ledger (connection, message id).
  • Missing: no index on transaction_categories.category_id alone for reverse lookups (rule apply); settlement_date not indexed (rewards effective date).
  • Parallel DML: V82 hit ORA-12839 on ADB; migrations now disable parallel DML.
  • N+1: mostly avoided via entity graphs (card.cardholder fixed 2026-09-01); getAllAccounts loop noted in memory as a batch candidate.

Performance-critical data flow (§58)

flowchart LR
  T[(transactions)] -->|Σ after anchor| B[BalanceMath]
  S[(statements)] -->|anchor| B
  T -->|window rows| R[RewardCalculationService]
  RR[(reward_rules)] --> R
  R -->|× cards| CP[Card Picker]
  IT[(investment_transactions)] -->|FIFO replay| P[Positions]
  CL[(classifications)] --> P
  CA[(corporate_actions)] --> P
  PR[(instrument_prices)] --> P
  P -->|× month ends| PV[portfolio_value datasource]
  P --> BB[Broker balance]
  B --> A["/accounts"]
  BB --> A

Every arrow is recomputed on each request. The two multiplicative nodes (Card Picker × cards, portfolio_value × month ends) are where cost grows fastest. The dropped tiered-rollup plan (memory 2026-09-01) would have cached the BalanceMath node; it was judged unnecessary because statement anchors already bound the sum.

Client performance

  • RSC prefetch and hydration remove the client waterfall; staleTime 30 s avoids refetch on navigation.
  • Server pagination everywhere (50/20/25); no full-table client loads (a binding convention from memory).
  • Debounced search (250/300 ms); job polling 1.5 s while running, 4 s and 30 s otherwise.
  • Faro Web SDK adds ~60 KB; Serwist caches static assets only.
  • Filters live in React state, so back-navigation re-fetches with defaults (only /jobs uses URL params).

Sections 25 and 59

25Testing strategy and test-to-rule map

Executive summary

Three tiers exist: ~660 server unit tests (JUnit 5 + Mockito, no Spring context), 62 client vitest suites (jsdom), and 651 Playwright E2E tests against a real Oracle Free container with WireMock for Gmail, Google, Yahoo, AMFI and a scripted LLM. The E2E suite is the only layer that boots Spring and runs Flyway, and it covers every one of the 193 API operations and 37 routes. Unit coverage is deep for rewards, loans math, categorization and statement parsing, and absent for XIRR, the loan and lending service layers, and the report SQL builder's category join. Confirmed

Critical untested logic

  2. Report category fan-out: no test asserts totals with multi-category transactions.

Where to look

  • Request correlation: copy X-Request-Id from the browser network tab, search Loki {job="financeos"} |= "<id>".
  • Jobs: /jobs page shows payload, result JSON, attempts, error; rows purge after 30 days.
  • Gmail ledger: per-message status via Settings → Gmail → Needs Attention; full table only in DB.
  • LLM: /settings/llm health panel (provider status, cooldown until, last error).
  • DB: connect with the wallet as the app user; v_chat_* views are handy read models.
  • Client: Faro errors and console logs in Grafana under app_id/kind labels.

What is not observable

  • No business metrics: transactions ingested per day, categorization accuracy, reward totals, price staleness.
  • No tracing spans; correlation is by request id only, and job execution has a job id but no link back to the enqueuing request.
  • LLM token usage: recordLlmTokens exists but is never called; per-day quota consumption is only visible through cooldown state.
  • Client Loki tier is empty (memory 2026-09-03), so client logs effectively do not ship.
  • Gmail per-message failures are counted, not alerted, until they reach FAILED_PERMANENT.
  • Price refresh success per instrument is logged but not surfaced in the UI (no "as of" date on values).
  • Audit coverage is limited to single-transaction mutations.

Grafana gotchas (from memory)

  • Loki proxy is GET-only; a POST error looks like an empty result.
  • The free instance sleeps; the first query returns 503 and needs a retry.
  • Faro data lives under app_id / kind labels, not service.
