Gotchas for newcomers

  • Mockito tests never boot Spring or Flyway. Always boot the server after schema or config changes.
  • Client tests need Node 20; the default Node 18 crashes vitest.
  • Amounts are positive in the DB with a type; the API re-signs them. Do not add signs in SQL without checking the three existing CASE expressions.
  • Each sub-repository has its own git; use git -C when diffing.
  • A new entity is not tenant-safe until it has @Filter(name="userFilter").
  • Migrations must be idempotent PL/SQL and must not use parallel DML on ADB.
  • Regenerate schema.d.ts after any DTO change or CI fails on drift.
  • Radix asChild triggers drop streamed RSC children; use children plus triggerClassName.
  • The READMEs describe an older architecture; trust this handbook and the code.

70If you only read ten things, the mental model, and a self-critique

If I only read ten things

  1. The ledger is transactions, everything else is derived. Balances, rewards, positions, schedules and reports are recomputed on every read from source rows. There are no cached totals to go stale, and no cached totals to protect you from a wrong formula. §10
  2. Trust is a state, not a boolean. Every ingested row carries a review status and reasons; the statement is the reconciliation truth that promotes alerts. Manual rows are trusted by definition. §38
  3. Tenancy is enforced three ways (Hibernate filter, explicit binds, Oracle-side context for chat) and swept by E2E for every endpoint. It is the most trustworthy part of the system. §15
  4. The credit-card model is on its third design (account → cardholder → card). Reward scoping, Gmail resolution and statements all hang off it; touch it carefully. M1
  5. Rewards are a rules engine with an exclusive chain and shared caps, evaluated per transaction with a reason code. Duplicate rules double-pay; point value defaults disagree between the report and the Card Picker. M7
  6. Reports over-count multi-category transactions because of a join fan-out; chat does not. When two numbers disagree, this is the first suspect. §45 C1
  7. Google OAuth never checks state. This is the one security finding to fix before anything else. §23
  8. XIRR has no tests and uses doubles. Every return figure rests on it. §25
  9. Everything asynchronous is a job in the DB run by two threads in the API JVM; failures surface in job results and the Gmail attention queue, not in alerts. §14
  10. The plans directory is intent, the code is truth, and they disagree in known places (charges in cost basis, EMI match tolerance, is_excluded). The READMEs are stale. §45 §31

The mental model

Picture a single append-mostly ledger of money movements per person, fed by three intakes of decreasing trust: hand entry, bank statements, and LLM-read emails. Around the ledger sit five calculators that never store their answers: a balance calculator anchored to statements, a reward calculator that replays card rules, a portfolio calculator that replays trades and corporate actions in FIFO order, a loan calculator that regenerates amortization schedules, and a report engine that aggregates whatever it is pointed at. A job queue in the same process does the slow intake work on a timer. A model can be asked questions and answers by writing SQL against read-only views that already carry the tenant boundary. The whole thing runs on free tiers, so quotas, cooldowns and small heaps shape many of its behaviours. If a number looks wrong, the question is never "which cache is stale" but always "which source row is wrong, or which formula".

Final master summary

FinanceOS is a single-person-scale personal finance system for an Indian household: a Spring Boot API over Oracle with a Next.js client, that ingests money movements from Gmail alerts and statements, lets the owner review and categorize them, and derives balances, credit-card rewards, investment positions, loan schedules, reports and chat answers on demand. It is well isolated per tenant, well tested at the wiring level, and deployed through a strict pipeline to a single small VM. Its financial numbers are trustworthy for balances, card dues, F&O and lendings; need a second look for rewards, positions and loans versus outside sources; and are known-wrong for category-grouped report totals with multi-category rows and unverified for XIRR. The three actions with the best return are validating OAuth state, fixing the category join, and writing XIRR goldens. Beyond that, the codebase would benefit most from deleting its dead code, reconciling its duplicated logic, and committing the large body of reviewed but unshipped work.
