38State machines & lifecycles

Executive summary

Seven entities carry meaningful states. Only one (job status) has a DB CHECK on its values and a guarded transition; the review state machine is guarded in a single Java class; the Gmail ledger, account, card, loan and LLM key states are enforced by service code or derived from dates with no transition log anywhere. Confirmed

Transaction review

stateDiagram-v2
  [*] --> NA : manual create
  [*] --> NEEDS_REVIEW : ingested (UNRECONCILED) or categorized by unverified rule/LLM (CATEGORY_UNVERIFIED) or duplicate flagged
  NEEDS_REVIEW --> NEEDS_REVIEW : clearReason but reasons remain

39Temporal and date logic audit

Executive summary

Business dates are calendar dates (LocalDate ↔ Oracle DATE) everywhere; system timestamps are Instant ↔ TIMESTAMP WITH TIME ZONE, which took three fix passes to get right. Cron schedules and price code pin Asia/Kolkata explicitly. The gaps are the places that call bare LocalDate.now() (report ranges, XIRR terminal flow, chat quota), which resolve in the JVM default zone and, if production runs in UTC, shift "today" by 5.5 hours. The client parses YYYY-MM-DD as local calendar dates and pins TZ=Asia/Kolkata in tests. Confirmed; production JVM zone Unknown.

40Rounding and money precision audit

Executive summary

Money is BigDecimal in Java and NUMBER(19,4) in Oracle with two scale-2 exceptions; quantities are 8 decimals; rates are stored as percents. Rounding happens at well-defined points inside each engine (HALF_UP unless a reward rule chooses FLOOR) and, for display, once in the client at 2 decimals. The exceptions worth knowing: XirrCalculator uses doubles; client card utilization and the reward rule tester use JavaScript numbers; SQL report aggregates pass through unrounded; the in-memory KPI path rounds differently from the SQL path. Worked example: one purchase through every layer

Purchase ₹1,000.00 on a card with a ₹100.00 convenience fee, rule 2 % EXCLUDE_FEE, NONE rounding, ₹50/month cap with ₹40 already used stored: amount 1000.0000 DEBIT, convenience_fee 100.0000 basis: 1000.0000 − 100.0000 = 900.0000 raw: 900.0000 × 2 / 100 = 18.000000 (scale 6) rounded: 18.00 (scale 2 HALF_UP) clamp: remaining = 50 − 40 = 10.00 → award 10.00 PARTIAL_CAP report: cashbackInr += 10.00; fees += 100.00; effective = gross + discounts − fees display: formatMoney → "₹10.00"; balance shows −₹1,000.00 (fee is inside the amount)
Same purchase in a report KPI "spend this month" with a category filter matching two of its categories SQL: SUM(CASE type='CREDIT' THEN amount ELSE −amount END) over the fanned-out join → −2,000.0000 (double counted) client: formatMeasureValue → "−₹2,000.00" chat: v_chat_transactions LISTAGG → one row → −1,000.00

Findings

  • High Category fan-out changes totals, not rounding, but it is the largest numeric discrepancy in the system.
  • Medium XirrCalculator is double-precision and untested; acceptable for a percentage but worth a golden test.
  • Medium KPI comparison rounding and defaults differ between SQL and in-memory datasources.
  • Medium Scale-2 columns (account_broker_details.cash_balance, sips.amount) vs scale-4 elsewhere.
  • Low Client float math for utilization and the reward tester is display-only.
  • Low Rates stored as percent (8.5000) consistently; a future fraction-scale column would be a ×100 trap.
  • No integer overflow risk: all money is BigDecimal / NUMBER(19,4) (max ~10^15).
  • Currency: every column defaults INR; instruments.currency exists but no conversion logic anywhere. Multi-currency is not implemented. Confirmed
