Section 15

15Authentication, authorization & multi-tenancy

Executive summary

One shared Spring Boot backend serves every user's financial data from the same Oracle tables, and the client (Vercel) and API (OCI VM) are different origins. This module therefore answers three load-bearing questions: who is asking (an opaque FINANCEOS_SESSION cookie resolved by Spring Session JDBC), which rows may they touch (a Hibernate @Filter switched on automatically by an AOP aspect for 36 entities), and how do two origins share one cookie (the Next.js server re-mints the API's cookie on its own origin). There are no roles: every user has identical authority over their own data and none over anyone else's. Confirmed

Quality is high for the tenancy and deletion designs (declarative filter, delete-then-verify in one transaction, a build-time schema test). Three real gaps stand out: the Google OAuth state is generated but never validated Critical; two Gmail bookkeeping entities lack the tenancy filter Medium; and maximumSessions(5) has no session-registry cleanup Medium.

Login CSRF gap. Critical The code logs stateValidated=false and the comment says state "is carried for correlation only (flowId) and is not verified against session state". Nothing checks that the browser completing the exchange started it. The callback is a GET, so OriginValidationFilter (unsafe methods only) does not apply. Google's single-use, short-lived codes narrow the window but do not close it. No exploit steps are given here; the fix is the standard pre-redirect state cookie or session nonce. Confirmed

Section 8

08Server / backend deep dive

Executive summary

A single Spring Boot 3.3.4 process (Java 21) hosts the REST API, the job worker and three cron schedulers. Requests pass a servlet filter that stamps a request id, then Spring Security (origin validation, session restore, user-context resolution, authorization), then thin controllers that validate DTOs and delegate to @Transactional services, where an AOP aspect switches on the Hibernate tenancy filter before any repository call. Errors are mapped to one JSON envelope. Slow or external work is enqueued as a job. Confirmed

Deviations from the typical pattern

  • Asynchronous 202 responses. Statement upload, price refresh, rule apply, import commit and reconcile commit return {jobId}; the real work runs later in JobWorker with UserContext set manually. domain/job/JobWorker.runJob
  • Server-sent events. ChatController.streamChat returns an SseEmitter (290 s timeout) fed from a 4-thread pool with a 15 s heartbeat; the Next route relays it.
  • Cron threads have no user. Price refresh runs with an empty context and refreshes all users' instruments deliberately; Gmail sync wraps each connection in callAs(userId).
  • Ingestion bypasses TransactionService.createTransaction. Gmail and file ingestion save Transaction rows through the repository directly, so create-path validation (non-zero amount) does not apply to them.
  • Two tenancy mechanisms plus chat's third. Hibernate filter; explicit user_id binds in native SQL builders; Oracle SYS_CONTEXT for chat.
  • Google OAuth callback lands on the client, not this server, so the session cookie is minted on the client origin. Gmail-connect's callback lands on the server because the user is already logged in.
  • Full-history recompute on read for balances, positions, rewards and schedules, with in-memory pagination for reward lines and instruments.
  • Self-proxy idiom. CategorizationService and TransactionService inject a @Lazy reference to themselves so intra-class calls hit the transactional proxy (comments cite bugs F2/F3); AccountDeletionExecutor was split into a separate bean for the same reason.
  • Controller-layer aggregation. LoanController.getLoansSummary sums outstanding principal itself; RewardReportController slices lines in memory.
  • E2E profile backdoor. E2eControlController and ScriptedLlmClient exist only under @Profile("e2e"); the systemd unit activates prod only. Confirmed

Client callers fall into two families: Server Components and server actions use lib/apiClient.ts's *Api objects; client components use lib/api/client.ts (api.GET/POST…) inside TanStack hooks. The E2E suite exercises 193 of 193 operations in the exported spec. Confirmed

Section 14

14Background jobs & automation

Executive summary

All automation runs inside the single server JVM: three cron schedulers (Gmail ingest, price refresh, job retention), a two-thread job worker polling a DB queue every 2 s, two after-commit event listeners (price refresh after trades, Gmail reactivation after account or card changes), and the boot-time sweep that marks orphaned RUNNING jobs as failed. There is no external scheduler, no message broker, and no second instance, so nothing can double-run but nothing fails over either. Confirmed Job mechanics are detailed in M5.

Notes

  • Timezones: crons run in Asia/Kolkata; "today" inside handlers uses LocalDate.now(zone) for price code but bare LocalDate.now() for XIRR, reports and chat quota, which is the JVM default zone. Strongly inferred UTC in production.
  • Tenancy on worker threads: runJob sets UserContext from the job row; cron price refresh deliberately runs without a user and touches all users' instruments; GmailSyncJobHandler asserts the connection belongs to the job's user.
  • Cron-global jobs (user null) are invisible and uncancellable through the API.
  • Notifications: none server-side. Client toasts on job completion; chat completion may raise a browser notification when the tab is hidden.
  • Recalculation jobs: none exist. Balances, positions, rewards and schedules are computed on read, so there is nothing to recalculate.
  • Cleanup: job retention only. Gmail cleanup is user-initiated from the account form.
  • What is not automated: Gmail token revocation detection, corporate-action ingestion, dividend detection (manual scan), SIP execution, reconciliation of derived figures.
