01Executive overview

FinanceOS in one paragraph

FinanceOS is a self-hosted, multi-user personal-finance system for the Indian market (₹, Apr–Mar financial year, UPI, NSE/BSE, AMFI mutual funds). It keeps one ledger of every money movement across bank accounts, credit cards, broker accounts and cash, fed by three ingestion paths: hand entry, Gmail alert emails read by an LLM, and PDF or Excel statement uploads parsed by a heuristic engine. On top of that ledger it computes credit-card rewards under user-defined rules, tracks investment positions and returns with FIFO lots and XIRR, amortizes loans and tracks peer lendings, lets the user build ad hoc reports and dashboards over eleven datasources, and answers natural-language questions through an LLM that writes SQL against tenant-scoped read-only views. It is a Spring Boot 3.3 / Java 21 / Oracle backend on one OCI virtual machine and a Next.js 16 / React 19 client on Vercel, joined by a session cookie relayed across origins. Confirmed

What problem it solves, and for whom

The evidence points to a single primary user who is also the developer: V2 seeds one admin user, signups are gated by a single shared invite code, and the operations runbook is written for one VM and one operator. Strongly inferred The product thesis, reconstructed from the transaction review workflow, is that ingestion is noisy and provisional: every automatically created transaction starts as "needs review" and is trusted only after a human, or a rule a human verified, confirms it. Statements are the reconciliation source of truth for Gmail alerts. Almost every derived figure (balance, position, reward, schedule) is recomputed from source facts on read rather than stored, a philosophy the plan documents name "recompute over incremental". Confirmed in code; the rationale appears only in plans and javadocs.

What makes it more than an expense tracker

  • Three ingestion paths with dedup and a reconciliation model
  • A credit-card reward engine that models real issuer mechanics (exclusive and additive rules, marginal tiers, shared cap buckets, milestones, anniversary windows)
  • Broker-statement reconciliation that separates intraday square-offs from delivery holdings using the broker's tax P&L
  • Corporate actions that rewrite FIFO lots (split, bonus, demerger, merger, cash in lieu)
  • A self-service report builder and an LLM chat over read-only, tenant-filtered views

Most important product concepts

  • Account (wallet or product) → Cardholder (person) → Card (plastic)
  • Transaction with unsigned amount plus DEBIT/CREDIT type, a review status and a set of review reasons
  • Source: manual, gmail_transaction_alert, gmail_statement, file_upload
  • Category rule with USER-over-LLM precedence
  • Holding as identity only; position derived by FIFO
  • Reward rule, cap bucket, milestone; reward computed on read
  • Loan schedule computed on read; lending as a signed ledger

Most important technical concepts

  • Hibernate userFilter enabled by an AOP aspect on every @Transactional method is the tenancy mechanism
  • Session cookie relay: the Next server re-mints the API's cookie on its own origin
  • RSC prefetch → hydrated TanStack Query cache → browser fetch through a rewrite
  • DB-backed job queue in the same JVM; cron schedulers for Gmail, prices, retention
  • Failover LLM client across free-tier providers
  • Chat SQL runs as CHAT_RO with SYS_CONTEXT tenancy inside Oracle
  • Flyway is authoritative; 85 migrations, idempotent PL/SQL since V63

Overall user journey

  1. onboardSign up with an invite code or sign in with Google (which also grants Gmail read access and creates a primary Gmail connection)
  2. set upCreate accounts (bank, credit card with cardholders and plastics, broker), set a Gmail "ingest from" date per account, allow-list bank sender addresses, add LLM keys if the shared free-tier keys are not enough
  3. ingestEvery two hours (10:00–22:00 IST) Gmail alerts become NEEDS_REVIEW transactions; statement uploads and Gmail statement attachments reconcile them; the LLM categorizes new rows and remembers merchant rules
  4. reviewApprove or fix categories in the review queue, merge duplicates, link transfers and refunds, verify rules
  5. configureModel each card's reward program; record trades, dividends, SIPs, corporate actions; add loans and lendings
  6. understandRead balances, rewards earned, positions and XIRR, EMI schedules; build reports and a dashboard; ask questions in chat; use the Card Picker before a purchase

FinanceOS in 5 minutes (for a new developer)

  1. Two repos, one folder. financeos-server (Spring Boot, port 6969, Oracle via Flyway) and financeos-client (Next.js, port 6970, proxies /api/v1/* to the server). Both have their own git history since 2025-12-31.
  2. Everything is per user. A request's user id sits in a ThreadLocal; an aspect enables a Hibernate filter so every entity read is scoped. If a service method is not @Transactional the filter is off. Six native-SQL sites bind user_id by hand. Chat has its own DB-level tenancy.
  3. The ledger is transactions. Unsigned amount plus type. Source tells you where it came from. review_type and a reason set tell you whether a human has trusted it. Categories are many-to-many. Links (transfer, refund, card payment) never mutate rows.
  4. Derived numbers are computed on read. Balance = statement anchor plus later transactions. Position = FIFO replay of trades and corporate actions. Reward = rule engine over the ledger. Loan schedule = annuity walk over terms and events. None of these are stored, so there is no cache to invalidate but every read pays the full cost.
  5. Slow work runs as jobs. Uploads, Gmail sync, price refresh, rule apply, import commits go through a DB-backed queue with two worker threads in the same JVM. The UI polls.
  6. LLMs are a utility, not the product. A failover client tries Gemini, Groq and OpenRouter in a user-configurable order for categorization, email extraction and chat. Chat writes SQL against 14 allow-listed v_chat_* views as a read-only Oracle user.
  7. The client renders twice. A Server Component fetches and seeds a TanStack Query cache; a client component hydrates it and does all later reads and writes. Filters live in component state; refresh loses them.
  8. Start reading here: TransactionService, ReviewStatusManager, HibernateFilterAspect, BalanceMath, RewardCalculationService, InvestmentService.calculateHoldingPosition, LoanScheduleService, GmailIngestionService, FailoverLlmClient, ChatOrchestrator, JobWorker, proxy.ts, lib/query/keys.ts. See Onboarding.

Apparent product philosophy

  • Provisional until confirmed. Ingested data is flagged, not trusted. Confirmed
  • Model reality, not a simplification. Cardholders vs plastics, marginal tiers, shared caps, intraday vs delivery, demerger cost carve-outs, cash in lieu. Confirmed
  • Recompute over incremental. Named in the loans and rewards plans and visible in every derived figure. Strongly inferred
  • Free-tier everything. LLM failover across free keys, a 1 GB VM with swap, Grafana Cloud Free. Strongly inferred from config comments and the runbook.
  • Defense in depth where it matters. Chat tenancy inside Oracle plus a SQL allow-list; account deletion verified against the data dictionary; ReDoS-safe regex rules. Confirmed
  • The reason a given workflow exists is recorded in plans/ and in unusually dense "why" comments, but not in any single product document. Where neither exists, this handbook says so.

Section 5

05Product architecture: core concepts

Executive summary

Twenty-odd concepts explain most of FinanceOS. Each is derived from an entity or a computed structure in the code, not assumed. The single most important mismatch between product and implementation is that the product concepts users think of as stored values (balance, position, reward earned, EMI schedule) are computed on read; the stored facts are transactions, trades, terms and rules.
