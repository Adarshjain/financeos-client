Module

M6Investments: instruments, prices, positions, returns, dividends, SIPs, corporate actions, F&O, imports

Executive summary

The portfolio tracker for stocks, ETFs and mutual funds held in "broker" accounts. A user maintains an instrument catalog (symbol, exchange, ISIN, AMFI code, Yahoo ticker), records buy and sell trades with itemized charges, and sees positions (FIFO lots, average cost, current value, realized and unrealized P&L, XIRR), dividends, and SIP progress. A daily job at 19:00 IST refreshes prices from AMFI (mutual funds) and Yahoo Finance (stocks, ETFs). Corporate actions (split, bonus, demerger, merger with fractional cash-in-lieu) rewrite lots without re-entering trades. F&O is a standalone realized-only ledger. Broker exports are imported through two pipelines: a plain importer (used in practice only for mutual-fund CAS PDFs) and a reconciliation pipeline that uses the broker's tax-P&L statement to separate intraday square-offs from delivery holdings. Confirmed

Two facts shape everything: nothing about a position is stored (every read replays all trades and corporate actions through FIFO), and charges are excluded from cost basis (only XIRR is fee-aware), which contradicts the original plan document. Dependents: net worth via HoldingValuationService.getBrokerMarketValue, the report datasources positions / realized_lots / portfolio_value / fno_trades, the chat portfolio tool, and the investments pages.

Calculation: FIFO position engine

domain/investment/InvestmentService.calculateHoldingPosition:427-762 builds one date-sorted timeline per holding and walks it once. Same-day order: CA-seeded lots (0) → corporate actions (1) → transactions (2), so a CA applies to the lots that existed before that day's trades.

  • Day collapse: when a trade_settlement_classifications row exists for (broker, instrument, day), that day's raw rows collapse into at most one synthetic delivery buy and one delivery sell (residual after removing intraday quantity and value); the intraday net (sell value − buy value) goes straight to intradayRealized and to an XIRR flow of sell − buy − dayCharges.
  • Buy: push Lot(qty, costPerUnit = price, buyDate). Cost excludes charges (comment at line 601: "Clean cost basis"). XIRR outflow = qty×price + charges.
  • Sell: consume oldest lots; per lot emit a RealizedLot (buy date, sell date, qty, values, P&L, holding days, term = days > 365 ? long : short). Realized = qty×sellPrice − matched cost (gross). XIRR inflow = qty×price − charges. If lots run out, log a warning and stop; the remainder is silently dropped from realized P&L.
  • Corporate action: split/bonus multiply qty by ratioTo/ratioFrom and divide cost per unit by it (openCost invariant); demerger multiplies parent cost per unit by 1 − pct/100; merger clears all lots.
openQty = Σ remainingQty (scale 8) openCost = Σ remainingQty × costPerUnit (scale 4) avgCost = openCost / openQty (scale 4 HALF_UP; 0 if no qty) currentValue = openQty × latestPrice | openCost ("at cost" if no price row) | null (qty 0) unrealized = currentValue − openCost; unrealizedPct = unrealized / openCost × 100 (scale 2) absoluteReturnPct = (currentValue − openCost + realized + intradayRealized + dividends) / openCost × 100

Example (RealizedLotsParityTest): buy 10 @ ₹100, buy 20 @ ₹150, sell 15 @ ₹200 → first lot fully consumed (10 × 100 = ₹1,000), 5 from the second (5 × 50 = ₹250) → realized ₹1,250; open 15 @ ₹150, openCost ₹2,250. The holding's realized always equals Σ per-lot P&L because both come from the same loop (parity contract with the reports engine).

Invisible-fee example: buy 100 @ ₹500 delivery. flows: buy −(qty×price + charges) @ tradeDate | sell +(qty×price − charges) | dividend +amount (gross, TDS not subtracted) @ payDate intraday net per classified day | merger bridge / cash-in-lieu @ ex_date | terminal +currentValue @ LocalDate.now() solver: Newton from 10%, ≤100 iterations, tol 1e-7; guards rate ≤ −0.9999 and |f'| < 1e-12 fallback bisection on [−0.9999, 10.0], ≤100 iterations, tol 1e-6; null if no sign change basis: Actual/365 (days / 365.0); result ×100, HALF_UP 2 dp; null for <2 flows, same-sign flows, or NaN

Reconciliation algorithm (two sources)

  1. dedupExecutions (tradebook) deduped by the full tuple (tradeId, orderId, date, isin, type, qty, price, time); tradeId alone is not unique
  2. classifyTax-P&L rows bucketed INTRADAY / STCG / LTCG / BUYBACK / FNO → intradayMap[isin][date] = {qty, buyValue, sellValue}
  3. splitPer (scrip, day), walk executions in order: intraQty = min(remaining target, e.qty), rest delivery; split rows get refs suffixed -I / -D
  4. eventsDay-level delivery events by value subtraction: delivBuyQty = dayBuyQty − intradayQty, delivBuyVal = dayBuyVal − intraBuyVal

  6. commitWrites investment_transactions (source import, charges verbatim), trade_settlement_classifications (insert-if-absent only, never updates), fno_trades; fires a price refresh per instrument

Module

M7Credit-card rewards engine

Executive summary

Answers three questions for an Indian credit-card user: what did I actually earn (rewards report and per-transaction lines), what would this swipe earn (rule tester and simulator), and which of my cards should I use (the Card Picker). It is a single stateless, compute-on-read engine: nothing about "how much a transaction earned" is ever stored. Every report, lines page or recommendation re-runs the user's rule set over the ledger. Confirmed domain/reward/RewardCalculationService.java:47-55 (javadoc: "Pure compute-on-read rewards calculator. No persisted reward state").

Why it exists: Indian issuer cards have idiosyncratic rate, cap, tier and milestone shapes (Axis ACE shared caps, Amex slab points, HDFC Infinia tiers); the research doc in plans/credit-card-reward-calculation-research.md catalogues 16 issuers and the engine primitives were derived from it. Strongly inferred from plan docs; the code itself does not state the rationale.

Level 1 · Product view

Who uses it

A cardholder with one or more credit cards who wants to know real earned value and to pick the best card per purchase.

What they configure

Reward rules (match conditions + accrual), cap buckets shared across rules, milestones, and per-account settings (anniversary date, default reward type, point value in ₹).

What they get

Per-account report (cash ₹ and points kept separate), per-transaction lines with a reason code, cap and milestone status, per-cardholder split, ranked card recommendations.

Product model vs implementation model. Users think "my card". Code has two things: Account (the card product or line, e.g. "HDFC Infinia") and Cardholder (the person swiping: primary or add-on). A physical plastic is a third thing, Card. Reward scoping keys off account + cardholder, never off the plastic, so a lost-card reissue never disturbs reward configuration. Confirmed V82 rewrote reward_rules.card_id to cardholder_id (V82__credit_card_model_v2.sql:128-138).

Users also assume "one deal per transaction". In code a transaction can earn under several rules at once: one exclusive winner plus every matching additive bonus, each with its own cap. A transaction id is therefore not a unique key for a report row.

Precedence: exclusive chain, additive stack

There is no single total order across all rules. resolveTxnFacts() partitions matching rules by stacking: RewardCalculationService.java:449-525

  1. EXCLUSIVE rules in descending priority (ties by created_at ascending) form a first-match chain. A 0% exclusive rule that matches wins and blocks everything below it (this is how "no rewards on rent" is modelled). If the winner's cap is exhausted: FALL_THROUGH (default) tries the next exclusive rule; STOP emits a zero line and ends the chain.
  2. ADDITIVE rules each accrue, clamp against their own cap, and always emit a line, stacking on the exclusive result. Priority among additive rules is cosmetic.

Worked example from RewardRecommendationServiceTest.exclusiveFallThrough_plusAdditiveStacking: 5% exclusive with a ₹0 cap (exhausted) falls through to a 1% exclusive base (₹10 on ₹1,000), plus a 0.5% additive bonus (₹5) → ₹15 across two lines. The reorder endpoint reassigns priority = N…1 from the UI order, so drag order is the exclusive-chain order. RewardRuleService.reorder():139-164

Executive summary

M10LLM platform & Chat with your data

Executive summary

FinanceOS calls third-party LLMs (Google Gemini, Groq, OpenRouter) for two background tasks, transaction categorization and Gmail email extraction, and for one interactive feature, "Chat with your data". Because no provider is paid for centrally, the LLM layer is built around failover across free tiers: FailoverLlmClient walks an ordered list of (provider, model, key) "buckets", skipping any in cooldown, so a single free key or the user's own bring-your-own keys keep the app working across daily quota resets. Strongly inferred from config comments ("widest free-tier headroom").

Chat is a bounded tool-calling loop (6 iterations, 180 s soft, 270 s hard, 290 s transport) in which the model writes read-only SQL executed as a separate Oracle user CHAT_RO that can see only tenant-filtered v_chat_* views. The model never sees raw data except what a capped query returns. Transcripts are held only in React state and are lost on refresh. Confirmed
