Module

M6Investments: instruments, prices, positions, returns, dividends, SIPs, corporate actions, F&O, imports

Executive summary

The portfolio tracker for stocks, ETFs and mutual funds held in "broker" accounts. A user maintains an instrument catalog (symbol, exchange, ISIN, AMFI code, Yahoo ticker), records buy and sell trades with itemized charges, and sees positions (FIFO lots, average cost, current value, realized and unrealized P&L, XIRR), dividends, and SIP progress. A daily job at 19:00 IST refreshes prices from AMFI (mutual funds) and Yahoo Finance (stocks, ETFs). Corporate actions (split, bonus, demerger, merger with fractional cash-in-lieu) rewrite lots without re-entering trades. F&O is a standalone realized-only ledger. Broker exports are imported through two pipelines: a plain importer (used in practice only for mutual-fund CAS PDFs) and a reconciliation pipeline that uses the broker's tax-P&L statement to separate intraday square-offs from delivery holdings. Confirmed

Two facts shape everything: nothing about a position is stored (every read replays all trades and corporate actions through FIFO), and charges are excluded from cost basis (only XIRR is fee-aware), which contradicts the original plan document. Dependents: net worth via HoldingValuationService.getBrokerMarketValue, the report datasources positions / realized_lots / portfolio_value / fno_trades, the chat portfolio tool, and the investments pages.

Calculation: FIFO position engine

domain/investment/InvestmentService.calculateHoldingPosition:427-762 builds one date-sorted timeline per holding and walks it once. Same-day order: CA-seeded lots (0) → corporate actions (1) → transactions (2), so a CA applies to the lots that existed before that day's trades.

  • Day collapse: when a trade_settlement_classifications row exists for (broker, instrument, day), that day's raw rows collapse into at most one synthetic delivery buy and one delivery sell (residual after removing intraday quantity and value); the intraday net (sell value − buy value) goes straight to intradayRealized and to an XIRR flow of sell − buy − dayCharges.
  • Buy: push Lot(qty, costPerUnit = price, buyDate). Cost excludes charges (comment at line 601: "Clean cost basis"). XIRR outflow = qty×price + charges.
  • Sell: consume oldest lots; per lot emit a RealizedLot (buy date, sell date, qty, values, P&L, holding days, term = days > 365 ? long : short). Realized = qty×sellPrice − matched cost (gross). XIRR inflow = qty×price − charges. If lots run out, log a warning and stop; the remainder is silently dropped from realized P&L.
  • Corporate action: split/bonus multiply qty by ratioTo/ratioFrom and divide cost per unit by it (openCost invariant); demerger multiplies parent cost per unit by 1 − pct/100; merger clears all lots.
openQty = Σ remainingQty (scale 8) openCost = Σ remainingQty × costPerUnit (scale 4) avgCost = openCost / openQty (scale 4 HALF_UP; 0 if no qty) currentValue = openQty × latestPrice | openCost ("at cost" if no price row) | null (qty 0) unrealized = currentValue − openCost; unrealizedPct = unrealized / openCost × 100 (scale 2) absoluteReturnPct = (currentValue − openCost + realized + intradayRealized + dividends) / openCost × 100

Example (RealizedLotsParityTest): buy 10 @ ₹100, buy 20 @ ₹150, sell 15 @ ₹200 → first lot fully consumed (10 × 100 = ₹1,000), 5 from the second (5 × 50 = ₹250) → realized ₹1,250; open 15 @ ₹150, openCost ₹2,250. The holding's realized always equals Σ per-lot P&L because both come from the same loop (parity contract with the reports engine).

Invisible-fee example: buy 100 @ ₹500 delivery. Groww charges: brokerage min(0.1%, ₹20) = ₹20; STT 0.1% = ₹50; exchange 0.00297% ≈ ₹1.49; SEBI ₹0.05; stamp 0.015% = ₹7.50; GST 18% of (brokerage + exchange + SEBI + DP) ≈ ₹3.88; total ≈ ₹82.91. Dividend receipt reconciliation

A dividends row is an expectation: Yahoo events times quantity held (suggested), a CAS line (import) or a hand-typed entry (manual). V89 adds the question "did the money actually arrive?", answered by linking the row to the bank credit it arrived as. The link is a direct nullable FK dividends.transaction_id (same pattern as lendings.transaction_id); the dividend amount is never changed by linking, it stays the gross figure the XIRR and FY summaries use. Several dividend rows may share one credit (an interim and a special payout often land as a single credit). domain/investment/dividend/DividendReceiptService.java

Status is derived at read time, not stored. Only two states are stored, in receipt_status, as a manual note: received_untracked (it landed in a bank account FinanceOS does not track) and not_received (confirmed missing). The other four come from DividendReceiptWindows.derive in this order: linked → received; manual note → that note; expected-payout window has not ended (end ≥ today) → awaiting; window end ≤ the user's bank coverage (MAX(transaction_date) over their bank_account transactions, from DividendReceiptStatusResolver) → overdue; otherwise unverifiable. "Unverifiable" exists because absence of a credit proves nothing when the statements stop before the window ends: the bank data has simply not reached that date, so the row is neither confirmed nor overdue. The chat dictionary uses the same wording ("not matched yet", never "missing").

Matching is suggestion only. GET /reconciliation proposes credits; the user confirms each (or "Confirm all"); nothing links automatically. Confirmed by code

Reconciliation algorithm (two sources)

  1. dedupExecutions (tradebook) deduped by the full tuple (tradeId, orderId, date, isin, type, qty, price, time); tradeId alone is not unique
  2. classifyTax-P&L rows bucketed INTRADAY / STCG / LTCG / BUYBACK / FNO → intradayMap[isin][date] = {qty, buyValue, sellValue}
  3. splitPer (scrip, day), walk executions in order: intraQty = min(remaining target, e.qty), rest delivery; split rows get refs suffixed -I / -D
  4. eventsDay-level delivery events by value subtraction: delivBuyQty = dayBuyQty − intradayQty, delivBuyVal = dayBuyVal − intraBuyVal
  5. fifoDelivery-only FIFO per scrip; unmatched sells → DATA_GAP; classifier delivery sells exceeding the tradebook → synthesized CA_EXIT_ sell at average price with OFF_MARKET_EXIT (buybacks, tenders)
  6. commitWrites investment_transactions (source import, charges verbatim), trade_settlement_classifications (insert-if-absent only, never updates), fno_trades; fires a price refresh per instrument

Example (IntradayClassificationTest.partialIntraday_straddlingBuy_isSplit): buy 15 @ ₹100 and sell 10 @ ₹110 same day with classifier intraday 10 → the buy splits into 10 intraday + 5 delivery; holdings show 5 @ ₹100; intraday P&L ₹100 stays out of cost basis. The Java matches scripts/reconcile_trades.py and adds per-execution tagging, off-market exits and snapshot validation. Without a tax-P&L file everything is treated as delivery. The per-row settlement_type is a display hint that "will lie on mixed straddle days" (V40 comment); recomputeClassificationForDay rebuilds the authoritative day row after every manual create, update or delete using min(intraday buys, intraday sells).

M7Credit-card rewards engine

Executive summary

Answers three questions for an Indian credit-card user: what did I actually earn (rewards report and per-transaction lines), what would this swipe earn (rule tester and simulator), and which of my cards should I use (the Card Picker). It is a single stateless, compute-on-read engine: nothing about "how much a transaction earned" is ever stored. Every report, lines page or recommendation re-runs the user's rule set over the ledger. Confirmed domain/reward/RewardCalculationService.java:47-55 (javadoc: "Pure compute-on-read rewards calculator. No persisted reward state").

Why it exists: Indian issuer cards have idiosyncratic rate, cap, tier and milestone shapes (Axis ACE shared caps, Amex slab points, HDFC Infinia tiers); the research doc in plans/credit-card-reward-calculation-research.md catalogues 16 issuers and the engine primitives were derived from it. Strongly inferred from plan docs; the code itself does not state the rationale.

A cardholder with one or more credit cards who wants to know real earned value and to pick the best card per purchase.

What they configure

Reward rules (match conditions + accrual), cap buckets shared across rules, milestones, and per-account settings (anniversary date, default reward type, point value in ₹).

What they get

Per-account report (cash ₹ and points both shown; points valued at the card's point value count toward the ₹ gross), per-transaction lines with a reason code, cap and milestone status, per-cardholder split, ranked card recommendations.

Product model vs implementation model. Users think "my card". Code has two things: Account (the card product or line, e.g. "HDFC Infinia") and Cardholder (the person swiping: primary or add-on). A physical plastic is a third thing, Card. Reward scoping keys off account + cardholder, never off the plastic, so a lost-card reissue never disturbs reward configuration. Confirmed V82 rewrote reward_rules.card_id to cardholder_id (V82__credit_card_model_v2.sql:128-138).

Users also assume "one deal per transaction". In code a transaction can earn under several rules at once: one exclusive winner plus every matching additive bonus, each with its own cap. A transaction id is therefore not a unique key for a report row.

Precedence: exclusive chain, additive stack

There is no single total order across all rules. resolveTxnFacts() partitions matching rules by stacking: RewardCalculationService.java:449-525

  1. EXCLUSIVE rules in descending priority (ties by created_at ascending) form a first-match chain. A 0% exclusive rule that matches wins and blocks everything below it (this is how "no rewards on rent" is modelled). If the winner's cap is exhausted: FALL_THROUGH (default) tries the next exclusive rule; STOP emits a zero line and ends the chain.
  2. ADDITIVE rules each accrue, clamp against their own cap, and always emit a line, stacking on the exclusive result. Priority among additive rules is cosmetic.

Worked example from RewardRecommendationServiceTest.exclusiveFallThrough_plusAdditiveStacking: 5% exclusive with a ₹0 cap (exhausted) falls through to a 1% exclusive base (₹10 on ₹1,000), plus a 0.5% additive bonus (₹5) → ₹15 across two lines. The reorder endpoint reassigns priority = N…1 from the UI order, so drag order is the exclusive-chain order. RewardRuleService.reorder():139-164

M8Loans, lendings & obligations

Executive summary

Three kinds of "money owed on a schedule": formal loans (home, car, personal, education, gold, two-wheeler, consumer durable, other) with a computed EMI amortization schedule, rate revisions, prepayments, foreclosure, itemized charges and bank-transaction matching; person-to-person lendings as a plain two-way ledger per counterparty (no interest, no schedule); and an obligations list (the Upcoming page, list and calendar views) merging upcoming and overdue EMIs and lending due dates with credit-card bills and expected statements. The plan doc explains the split: banks compute interest on a schedule, informal debts do not. Intent doc plans/loans-module-plan.md:13

The schedule is never stored; every read recomputes it from the loan's terms and events. Payments record only (installment seq, date, amount, transaction id); the interest/principal split shown everywhere is the schedule's theoretical split. Outstanding principal follows the schedule, not payments. Outside this module, loans and lendings are read by the notification producers, the Inbox EMI and lending collectors, ObligationsService and the net_worth report datasource (active loans' outstanding principal as liabilities, counterparties' net positions as assets or liabilities); see M11 · Home, Inbox & Upcoming. Match suggestions (GET /counterparties/{id}/match-suggestions)

Mirrors the loans EMI matching panel with the counterparty's own unlinked entries as targets. For each unlinked entry: candidate type = direction→DEBIT/CREDIT, amount within MatchingConstants.MATCH_AMOUNT_TOLERANCE (±₹20, the same constant the EMI matcher uses), date within MATCH_DATE_WINDOW_DAYS (±7) of entryDate, excluding any transaction already referenced by a loan/lending row (getAllReferencedTransactionIds — deliberately unfiltered by user, an exclusion set only, never surfaced to a client) and excluding transactions already sitting in a transaction_links group (a check the EMI matcher above does not do). Assignment is greedy: each candidate transaction goes to at most one entry — the one whose entryDate is nearest, ties broken toward the earlier entry in (entryDate, createdAt) order. Only entries with ≥1 surviving candidate are returned (the same lesson the loans panel already learned); candidates within an entry are ordered by |amount diff| then |date diff|. Deleting an event rejects if any payment's seq exceeds the new schedule length, but not if the seq now means a different installment. Foreclosure amount is unreconciled. Close has no zero-balance guard.
  • No @Version; TOCTOU windows on payment seq and transaction linking fall through to raw DB constraint errors. Re-posting addPayment without a seq settles the next installment (not idempotent); the UI always passes a seq. Batch re-post is rejected wholesale.
  • 400-vs-404 lesson (hit and reverted while building the linking feature, 2026-09-07): LendingService.getLendingAndVerifyOwnership briefly switched from findById (EntityManager.find, which bypasses the Hibernate userFilter that Lending has always carried) to the fetch-joined JPQL findWithRefsById — but that query is @Filter-scoped, so a foreign row is invisible and 404s before the ownership check runs, breaking the established "foreign row → 400 Security Breach" contract the rest of the module relies on (an existing E2E assertion caught it). Transactions datasource semantics

  • Amount is signed CREDIT positive, DEBIT negative. The spend measure is the same money spend-positive: CASE WHEN t.type = 'DEBIT' THEN t.amount ELSE -t.amount END (debits positive, refunds and income negative), so a spend chart needs no sign flip; it was added instead of changing the sign of amount. "Total spend" is SUM(spend) or SUM(amount) filtered to DEBIT.
  • Link type and card joins (fixed 2026-09-30). linkType is a joined column (lk.link_type from a per-transaction MIN over its links) because Oracle rejects a scalar subquery in GROUP BY (ORA-22818); grouping by it used to 500. The cards join is aliased cd: it and the categories join both used c, so card, cardholder or relationship combined with category could never run.
  • No default exclusions. isExcluded, isTransferLeg, isRefundLeg, isUnderMonitoring and reviewType are opt-in filters. The builder seeds isExcluded is false on a new transactions report as a UI convenience only; it is not re-applied on edit or on ad hoc runs from elsewhere.
  • isTransferLeg and isRefundLeg are correlated EXISTS subqueries (no fan-out).
  • The source and channel filter values come from TransactionSource and TransactionChannel (fixed 2026-10-04: source listed the dead "gmail"/"manual", channel was missing ATM). See Transactions.

Executive summary

FinanceOS calls third-party LLMs (Google Gemini, Groq, OpenRouter) for two background tasks, transaction categorization and Gmail email extraction, and for one interactive feature, "Chat with your data". Because no provider is paid for centrally, the LLM layer is built around failover across free tiers: FailoverLlmClient walks an ordered list of (provider, model, key) "buckets", skipping any in cooldown, so a single free key or the user's own bring-your-own keys keep the app working across daily quota resets. Strongly inferred from config comments ("widest free-tier headroom").

Chat is a bounded tool-calling loop (6 iterations, 180 s soft, 270 s hard, 290 s transport) in which the model writes read-only SQL executed as a separate Oracle user CHAT_RO that can see only tenant-filtered v_chat_* views. The model never sees raw data except what a capped query returns. Transcripts are held only in React state and are lost on refresh. Confirmed

Executive summary

Bills due card states

CardBillService.listBills now returns a row for every open credit card. A card without a live statement is an AWAITING_STATEMENT row (a new BillStatus, never notified): statement id, period, due date and totals are null, and only the account fields, unbilledAmount and nextStatementExpectedOn are set. GET /bills accepts an optional accountId filter (the account page uses it). The notification tick still calls build directly, so it never sees the awaiting rows and never pays for the two extra queries.

  • unbilledAmount: SUM of non-excluded DEBITs on the card dated after the live statement's period end (all of them for a card without a statement), floored at 0. Credits never reduce it, because payments and refunds count towards the open bill instead. Null when the statement has no period end.
  • nextStatementExpectedOn: the end of the BillingCycles cycle after the latest non-rejected statement with both period dates. It may already be in the past when the next statement is late.
  • Refunds pay the bill: a credit after the period end that is linked as REFUND or REVERSAL now counts towards paidAmount exactly like a CC_PAYMENT link (user decision). Unlinked credits are still only "possible payments".

Section isolation (SectionRunner)

Upcoming and the net_worth datasource are composite reads: several independent sections (four obligation kinds; accounts, loans, lendings). Each section was meant to degrade to "no rows" when it fails. A plain try/catch around the section was not enough: when the failing collaborator is a @Transactional bean that joined the caller's transaction (a service or a Spring Data repository), its interceptor has already marked that shared transaction rollback-only, and the caller's commit then throws UnexpectedRollbackException, so the whole read returned 500 despite the catch. The Spring/H2 integration tests in 9be54db found this.

SectionRunner.run(section) TransactionalSectionRunner: TransactionTemplate(PROPAGATION_REQUIRES_NEW, readOnly = true) caller's transaction suspended → section's collaborators join the new one failure → only the section's transaction rolls back → exception reaches the caller's catch → section yields [] SectionRunner.DIRECT: runs inline with no transaction (plain Mockito unit tests) events: obligations.section.failed (kind), report.net_worth.section_failed (section), report.net_worth.row_skipped (one account, loan or counterparty)

The section's own @Transactional collaborators enable the tenant filter on entry, on the new session. ObligationsSectionIsolationIntegrationTest makes the card-bill section throw and asserts EMI and lending rows still come back through the service proxy and over HTTP; NetWorthSectionIsolationIntegrationTest does the same for the loans and lendings sections through ReportDataService and the built-in widget endpoint. Confirmed
