Section 6

06Database deep dive

Executive summary

One Oracle schema (Autonomous DB in production, a local Oracle container in dev and E2E), migrated exclusively by 85 Flyway scripts; Hibernate ddl-auto is none, so Flyway, not the entities, is authoritative. It grew from a single-user MVP (V1 seeds one admin user in V2) into roughly 55 tables plus 16 read-only chat views covering the ledger, a three-layer credit-card model, Gmail and statement ingestion ledgers, a rebuilt investment stack, loans and lendings, a large reward-rule configuration, a job queue, LLM keys, and reports. Confirmed

Three schema-wide facts: primary keys are VARCHAR2(36) UUID strings (transactions and jobs self-assign UUIDv7); money is NUMBER(19,4) almost everywhere with two scale-2 exceptions; and every Instant-mapped column is now TIMESTAMP WITH TIME ZONE, which took three fix passes (V27, V46, V71) after ORA-18716 outages. No table has @Version or a soft-delete column; deletion is real and relies on FK cascades.

Chat views and the allow-list drift

V70 created the v_chat_* read-only views, each with WHERE user_id = SYS_CONTEXT('USERENV','CLIENT_IDENTIFIER') (instruments and prices are global), and grants SELECT to chat_ro idempotently. Later card-model migrations replaced v_chat_account_cards / v_chat_card_instances with v_chat_cardholders / v_chat_cards (V82). The migrations define 16 current views; ChatSqlValidator.ALLOWED_VIEWS lists 14 and omits V_CHAT_CARDHOLDERS and V_CHAT_CARDS, while dictionary.md tells the model about them. A query the model writes against those two views is rejected with TABLE_NOT_ALLOWED and it must self-correct. Confirmed by grep chat/db/ChatSqlValidator.java:18-33

Tenancy at the database level

  • 34 of 50 entities carry @Filter(name="userFilter", condition="user_id = :userId"), enabled by HibernateFilterAspect on every @Transactional method. Join tables and JobArtifact inherit through parents; GmailBackfillDemand is keyed by user id; GmailSyncCursor has a user_id and no filter.
  • Native SQL exists through EntityManager.createNativeQuery in six classes (AccountRepositoryCustomImpl, TransactionRepositoryCustomImpl, TransactionReferenceValidator, ChartReportExecutor, KpiReportExecutor, TableReportExecutor); each binds user_id explicitly or receives pre-filtered ids. The database analyst's grep for nativeQuery annotations found none; the createNativeQuery sites were confirmed separately. Confirmed
  • Chat uses Oracle-side enforcement (CHAT_RO + session identifier + view predicates), independent of the JVM filter.
  • No FK asserts that a transaction's account and card, or a rule's account and cardholder, belong to the same user or account; single-column FKs only.
  • V1-era tables (accounts, transactions, categories, holdings, statements, dividends) still have nullable user_id; a NULL row is invisible to the filter, a silent orphan. Every table from V26 onward declares NOT NULL. Strongly inferred single-user origin.

What the schema enforces, and what it does not

Enforced by Oracle

  • amount > 0 (direction in type)
  • One default dashboard, one primary cardholder, one open card per cardholder, unique open last4 per account (NULL-skipping functional unique indexes)
  • One processed row per (connection, message); one statement per (account, sha256) and per (account, period); one payment per (loan, seq); one loan or lending fact per transaction
  • Every user FK cascades (V79, data-dictionary driven)
  • reports.definition and dashboards.widgets are valid JSON

Application-only or nowhere

  • transaction.card belongs to transaction.account; rule.cardholder belongs to rule.account
  • Cap-bucket members share reward_type
  • Shape of tiers and eligibility JSON
  • Enum membership for gmail status, statement verdict, review reason, llm option_id
  • jobs.dedup_key uniqueness
  • Duplicate corporate actions
  • fno_trades.realized_pnl consistency after edits

Suspicious areas with evidence

  • Seven unindexed FK columns: category_rule_categories.category_id, reward_rule_categories.category_id, corporate_actions.target_instrument_id, trade_settlement_classifications.instrument_id (second column of a composite only), gmail_processed_messages.transaction_id, gmail_sync_cursors.sender_id (composite second column), and gmail_senders.account_id as reported by the database analyst (the column was dropped in V62, so verify before acting). V79's own comment explains why this matters: an unindexed FK makes Oracle share-lock and full-scan the child on parent DML. Medium
  • Schema drift: V81 defensively drops accounts.status and two CHECK constraints that no migration ever created, proof that a live environment carried an uncommitted prototype (the parked card-fees experiment). Confirmed
  • Legacy data landmine: transaction_review_reasons.reason = 'OTHER' from the V26 backfill has no enum constant; a surviving row fails hydration. Unknown whether any exist.
  • Dead code: CardRelationship enum (zero references). Cleanly removed tables: gmail_sync_state (V69), lending_repayments (V48), account_cards and card_instances (V82).
  • Short-lived design decisions: metadata CLOBs (V1→V6), instrument F&O columns (V43→V45), sender account binding (V19→V21→V23→V62), reward point_value (V51→V57), card due day and grace (V1→V83), statement card_id (V73→V82).
  • Derived-but-stored: investment_transactions.total_charges (safe, recomputed), fno_trades.realized_pnl (no recompute hook), transactions.applied_rule_id, statement summary fields, job results.
  • Hard resets: V35 dropped and recreated investment_transactions; V40 deleted every investment row ("no data to preserve").

Pattern: older enums got CHECK constraints at creation; newer Java-driven enums did not. From V63 onward every risky migration checks the data dictionary before acting, a direct consequence of Oracle DDL auto-commit leaving partial state when a migration fails.

Business meaning of the database

  • The ledger (transactions and satellites): every money movement, however it arrived.
  • The wallets (accounts, detail tables, cardholders, cards): where money lives and who holds which plastic.
  • The sources (Gmail tables, statements): ingestion machinery and the bookkeeping that prevents double ingestion.
  • The derived layers (reward configuration, holdings as identity, classifications): insight computed on read rather than stored.
  • The configuration (category rules, reward rules, reports, dashboards, LLM prefs): how the user teaches the app.
  • The operations tables (jobs, sessions, LLM keys): infrastructure.

36Data provenance: "explain this number"

Executive summary

For each important number a user sees, this section traces it from the pixel back to the stored fact and the external source, and states whether it can be proven correct. The recurring answer: the number is recomputed from source rows on every read, so "can I prove it" reduces to "can I prove the source rows and the formula". Where the formula lives in one place and has tests, confidence is high; where it is duplicated or untested, it is not. Confirmed

Account tile balance (e.g. "−₹3,000.00" on a credit card)

  1. UICreditCardTile.tsx renders formatNullableMoney(account.balance) and computes utilization as abs(balance)/creditLimit×100 in floating point
  2. cachekeys.accounts.list() hydrated by accounts/page.tsx; refetched on invalidation and router.refresh()
  3. APIGET /api/v1/accounts → AccountResponse.balance, balanceAnchored, reconciliationGap, anchorDate
  4. serviceAccountService.getAllAccounts → native findAccountBalanceBatches → BalanceMath.apply: for a card, base = −closing (if closing > 0) then + Σ(CREDIT +, DEBIT −) for transactions dated strictly after the anchor
  5. source rowsstatements (latest non-rejected with period_end and closing_balance) and transactions (all rows on the account; is_excluded ignored)
  6. originStatement closing balance parsed by SummaryFieldHarvester from a PDF; transactions from Gmail extraction, statement lines or manual entry

Provable? Yes for the formula (AccountBalanceEquivalenceTest, AccountServiceTest); the inputs are only as correct as the parser's closing balance and the completeness of post-anchor transactions. Excluded transactions are counted, contrary to the UI copy. Medium confidence

Rewards page "Effective value ₹12,450" and a line "₹18.00 · Dining 2 %"

  1. UIRewardsSummaryCards shows summary.effectiveValueInr; RewardLinesTable shows line.earned with reason
  2. APIGET /rewards/report and /rewards/lines
  3. engineRewardCalculationService.evaluate: expand window → fetch DEBIT transactions by COALESCE(settlement_date, transaction_date) → net refund links → per transaction resolve exclusive chain + additive rules → clamp to caps → per rule basis = amount − convenience fee if EXCLUDE_FEE → accrue PERCENT or SLAB or tiered → sum into cashbackInr, points, milestones → effectiveValueInr = gross + discounts − fees
  4. source rowstransactions (amount, type, dates, MCC, channel, EMI, intl, fee, discount, category joins, card → cardholder), transaction_links, statements (STATEMENT_CYCLE windows), reward_rules (+ join tables), reward_cap_buckets, reward_milestones, accounts (anniversary, point value)
  5. originRules typed by the user; transactions from ingestion or manual entry; categories from rules or LLM

Provable? The engine is one code path shared by report, lines and recommender, with numeric tests for fees, tiers, caps, scoping and anniversary windows. Nothing is stored, so there is no drift between a cached value and the source. Points shown as ₹ on the Card Picker use ₹0.25 by default; the report keeps points separate. High confidence in formula; correctness depends on category assignment and reward-input fields, which the review workflow governs.

Holdings "Current value", "Unrealized P&L", "XIRR 14.2 %"

  1. UIHoldingCard / HoldingSummaryMetrics render pos.currentValue, pos.unrealized, pos.xirr verbatim
