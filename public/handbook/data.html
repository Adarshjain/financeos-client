06Database deep dive

Executive summary

One Oracle schema (Autonomous DB in production, a local Oracle container in dev and E2E), migrated exclusively by 95 Flyway scripts; Hibernate ddl-auto is none, so Flyway, not the entities, is authoritative. It grew from a single-user MVP (V1 seeds one admin user in V2) into roughly 57 tables plus 16 read-only chat views covering the ledger, a three-layer credit-card model, Gmail and statement ingestion ledgers, a rebuilt investment stack, loans and lendings, a large reward-rule configuration, a job queue, LLM keys, reports and dashboards, notification markers, and the per-row Inbox state. Confirmed

Three schema-wide facts: primary keys are VARCHAR2(36) UUID strings (transactions and jobs self-assign UUIDv7); money is NUMBER(19,4) almost everywhere with two scale-2 exceptions; and every Instant-mapped column is now TIMESTAMP WITH TIME ZONE, which took three fix passes (V27, V46, V71) after ORA-18716 outages. No table has @Version or a soft-delete column; deletion is real and relies on FK cascades.

Chat views and the allow-list drift

V70 created the v_chat_* read-only views, each with WHERE user_id = SYS_CONTEXT('USERENV','CLIENT_IDENTIFIER') (instruments and prices are global), and grants SELECT to chat_ro idempotently. Later card-model migrations replaced v_chat_account_cards / v_chat_card_instances with v_chat_cardholders / v_chat_cards (V82). The migrations define 16 current views; ChatSqlValidator.ALLOWED_VIEWS lists 14 and omits V_CHAT_CARDHOLDERS and V_CHAT_CARDS, while dictionary.md tells the model about them. A query the model writes against those two views is rejected with TABLE_NOT_ALLOWED and it must self-correct. Confirmed by grep chat/db/ChatSqlValidator.java:18-33

V86 CREATE OR REPLACEs v_chat_lendings to add a transaction_id column (nullable — several lending rows can now share one, so it is not a join key on its own) and re-grants SELECT to chat_ro idempotently, the same guarded pattern V70 used (skips silently if chat_ro does not exist, e.g. on dev DBs). dictionary.md §9 documents the join to v_chat_transactions.id and states the rule chat needs: money lent/borrowed is not spend or income.

V89 CREATE OR REPLACEs v_chat_dividends to add source, transaction_id and receipt_status (stored manual note only; derived states are not in SQL), with the same guarded chat_ro grant. dictionary.md §6 now separates expected from received dividends.

Tenancy at the database level

  • 34 of 50 entities carry @Filter(name="userFilter", condition="user_id = :userId"), enabled by HibernateFilterAspect on every @Transactional method. Join tables and JobArtifact inherit through parents; GmailBackfillDemand is keyed by user id; GmailSyncCursor has a user_id and no filter.
  • Native SQL exists through EntityManager.createNativeQuery in six classes (AccountRepositoryCustomImpl, TransactionRepositoryCustomImpl, TransactionReferenceValidator, ChartReportExecutor, KpiReportExecutor, TableReportExecutor); each binds user_id explicitly or receives pre-filtered ids. The database analyst's grep for nativeQuery annotations found none; the createNativeQuery sites were confirmed separately. Confirmed
  • Chat uses Oracle-side enforcement (CHAT_RO + session identifier + view predicates), independent of the JVM filter.
  • No FK asserts that a transaction's account and card, or a rule's account and cardholder, belong to the same user or account; single-column FKs only.
  • Navigation-redesign queries (server 9e02b6c). InboxItemState carries the filter, and its repository methods (findByUserId, findByUserIdAndItemKey) also bind the user explicitly. The review and Gmail counts behind the Inbox summary rows (countByUserIdAndReviewType, countByUserIdAndReviewTypeAndReason, countByUserIdAndStatusIn) and the seeder's report lookup (findFirstByUser_IdAndNameAndDatasourceOrderByCreatedAtAsc) bind user_id explicitly. The card unbilled sums (sumIncludedDebitsAfter, sumIncludedDebits) are keyed by account id only. They are safe because CardBillService.listBills passes only the caller's own cards and the filter is active. The EMI and lending Inbox collectors call getAllLoansWithSchedule() and findAllWithRefs() with no user argument, so they rely on the filter alone. That holds because InboxService.list is @Transactional. markHomeSeeded is a bulk JPQL UPDATE on users (the root, no filter) keyed by the caller's id from UserContext. Confirmed
  • Per-section transactions keep the filter: SectionRunner (Upcoming and net_worth) runs each section in its own REQUIRES_NEW read-only transaction. A new session starts without the filter. Each section's collaborators (LoanService, LendingService, CardBillService, AccountService, Spring Data repositories) are @Transactional, so HibernateFilterAspect enables the filter again on the new session. A future section that queried through a non-transactional bean would run unfiltered. Strongly inferred from the aspect's pointcut.
  • V1-era tables (accounts, transactions, categories, holdings, statements, dividends) still have nullable user_id; a NULL row is invisible to the filter, a silent orphan. Every table from V26 onward declares NOT NULL. Strongly inferred single-user origin.

What the schema enforces, and what it does not

Enforced by Oracle

  • amount > 0 (direction in type)
  • One default dashboard, one primary cardholder, one open card per cardholder, unique open last4 per account (NULL-skipping functional unique indexes)
  • One processed row per (connection, message); one statement per (account, sha256) and per (account, period); one payment per (loan, seq); one loan fact per transaction — loan_events/loan_payments/loan_charges.transaction_id each stay globally unique after V86
  • Every user FK cascades (V79, data-dictionary driven)
  • reports.definition and dashboards.widgets are valid JSON
  • One Inbox state row per (user, item key), uq_inbox_item_state_user_key (V94)

Application-only or nowhere

  • transaction.card belongs to transaction.account; rule.cardholder belongs to rule.account
  • Cap-bucket members share reward_type
  • Shape of tiers and eligibility JSON
  • Enum membership for gmail status, statement verdict, review reason, llm option_id
  • jobs.dedup_key uniqueness
  • Duplicate corporate actions
  • fno_trades.realized_pnl consistency after edits
  • One lending fact per transaction was DB-unique through V85; V86 downgrades lendings.transaction_id to a plain index, so split bills (several lending rows, one transaction) are a TransactionReferenceValidator-only rule now, not a constraint — and no check anywhere sums their amounts against the transaction's own
  • Direction agreement between a lending row and its linked transaction (lent↔DEBIT, borrowed↔CREDIT) — service-only, same as loan-vs-lending exclusivity always was
  • Home seeded once per user: a conditional UPDATE on users.home_seeded_at serializes on the row lock. No constraint stops a second "Home" dashboard, and Restore deliberately creates one each time.
  • Widget kind/builtinKey/params shape and built-in minimum widths (DashboardValidator only)
  • Inbox item keys: any non-blank string of up to 200 characters with no whitespace is accepted by snooze, dismiss and undo. Keys are not checked against the rows the Inbox lists, so state can exist for keys that never appeared.

Suspicious areas with evidence

  • Seven unindexed FK columns: category_rule_categories.category_id, reward_rule_categories.category_id, corporate_actions.target_instrument_id, trade_settlement_classifications.instrument_id (second column of a composite only), gmail_processed_messages.transaction_id, gmail_sync_cursors.sender_id (composite second column), and gmail_senders.account_id as reported by the database analyst (the column was dropped in V62, so verify before acting). V79's own comment explains why this matters: an unindexed FK makes Oracle share-lock and full-scan the child on parent DML. Medium
  • Schema drift: V81 defensively drops accounts.status and two CHECK constraints that no migration ever created, proof that a live environment carried an uncommitted prototype (the parked card-fees experiment). Confirmed
  • Legacy data landmine: transaction_review_reasons.reason = 'OTHER' from the V26 backfill has no enum constant; a surviving row fails hydration. Unknown whether any exist.
  • Dead code: CardRelationship enum (zero references). Cleanly removed tables: gmail_sync_state (V69), lending_repayments (V48), account_cards and card_instances (V82).

Business meaning of the database

  • The ledger (transactions and satellites): every money movement, however it arrived.
  • The wallets (accounts, detail tables, cardholders, cards): where money lives and who holds which plastic.
  • The sources (Gmail tables, statements): ingestion machinery and the bookkeeping that prevents double ingestion.
  • The derived layers (reward configuration, holdings as identity, classifications): insight computed on read rather than stored.
  • The configuration (category rules, reward rules, reports, dashboards, LLM prefs): how the user teaches the app.
  • The operations tables (jobs, sessions, LLM keys): infrastructure.
  • The attention layer (notification markers on producer rows, inbox_item_state, users.home_seeded_at): what the app has already told the user and what the user chose to hide. The Inbox, Upcoming and Home figures themselves are computed on read and never stored.

Executive summary

The recurring answer: the number is recomputed from source rows on every read, so "can I prove it" reduces to "can I prove the source rows and the formula". Where the formula lives in one place and has tests, confidence is high; where it is duplicated or untested, it is not. Confirmed

Executive summary

Three ingestion paths feed one ledger; four derivation engines read it. Data is created at the edges (email, PDF, broker file, form), normalized once (LLM extraction, parser, import resolver), persisted as facts, and never aggregated into stored summaries. Enrichment happens in two places: LLM categorization at ingestion and corporate-action replay at read. Synchronization is one-directional from sources to the ledger; reconciliation exists only between Gmail alerts and statements. Confirmed
