Section 27

27Build, deploy and runtime

Executive summary

Two repositories, two hosts. The server jar is built by GitHub Actions, gated on the client's reusable E2E workflow, copied over SSH to a single OCI always-free VM and restarted under systemd behind Caddy (TLS via DuckDNS). The client deploys to Vercel Hobby on push. Flyway runs at boot against Oracle Autonomous DB; CI boots the server twice to prove migration idempotence. There is no staging environment, no blue/green, and no rollback beyond redeploying the previous commit. Confirmed from workflows and memory notes; the VM's systemd unit and Caddyfile are not in the repo.

Operational risks

  • Single VM, 952 MiB, swap active: one OOM or reboot is an outage; no HA.
  • Restart-in-place deploy: every deploy is downtime; a failed Flyway migration leaves the service down until fixed by hand.
  • No staging: E2E runs against Oracle Free, not ADB; ADB-specific behaviour (parallel DML) surfaced only in prod.
  • Secrets on the box: env in the systemd unit; wallet on disk; SSH key in GitHub secrets.
  • Cross-repo coupling: server deploy depends on the client repo's workflow being green and compatible.
  • Uncommitted work: as of 2026-09-06 a large body of reviewed work sits uncommitted or unpushed across both repos (memory); prod lags the working tree by weeks.

Sections 60, 61 and 62

60Evolution, architectural decisions and domain boundaries

Executive summary

The 85 migrations and the plans directory tell the system's history: a bank-transaction tracker (V1–V25) that grew Gmail ingestion, statements and review workflow (V26–V40), then investments, F&O and loans (V41–V50), then a full rewards engine (V51–V61), then LLM plumbing, chat and account lifecycle (V62–V85). Three areas were redesigned rather than extended: the credit-card model (three times), lendings (repayments → ledger), and the client data path (server-first → TanStack). Confirmed from migration files; dates from memory notes where present.

Well-separated: Wealth (its own brokers table, no coupling to bank transactions except the broker's balance), Debt (loans link to transactions only through payments), Core. Leaky: Insight reads every domain's tables directly through SQL (reports) and views (chat), so any schema change ripples into DatasourceCatalog, the executors and the v_chat_* views. Shared kernel: transactions is touched by Gmail, files, statements, categorization, rewards, loans and merge; it is the coupling point of the system.
