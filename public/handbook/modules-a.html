Module

M1Accounts, cards & identifiers

Executive summary

Accounts model "where money lives": bank accounts, credit cards, broker (demat) accounts and a generic bucket for cash and wallets. Everything else hangs off them: every transaction carries a mandatory account_id, statements attach to an account, Gmail alerts are matched to an account by last-4 or by user-declared identifier aliases, and reward rules scope to a cardholder under an account. A second sub-model, Cardholder → Card, records who holds a card (primary or add-on person) and which plastic they carry, so that reissuing a lost card or adding a spouse's card does not corrupt history or reward scoping. Confirmed

Balances are computed, never stored: the latest non-rejected statement's closing balance acts as an "anchor" and only later transactions are added on top; without an anchor the balance is opening balance plus the signed sum of all transactions. Broker "balance" is portfolio market value plus cash. Closure is a single closed_on date that blocks card mutations but not new transactions or imports. Confirmed domain/account/BalanceMath.java:29-82

Level 1 · Product view

Capabilities

  • Create, edit, close, reopen, delete accounts
  • Store statement passwords (encrypted at rest)
  • Set a Gmail "ingest from" date
  • Add identifier aliases for email matching
  • Manage cardholders and plastics; replace or close cards; bulk-reassign transactions between cards

Inputs

Name, type, type-specific details (opening balance and last4 for bank; credit limit, issuer, product for card; provider, client id, cash balance for broker), financial position and net-asset exclusion flags, close date, cardholder name/relationship/spend limit, card last4 and issue date.

Outputs

A sealed AccountResponse per type with a computed balance, anchor flag, reconciliation gap (bank), utilization (card), cardholders and cards; the card-cycle summary (dues, days until due, utilization, per-statement history).

  • Precision: bank and card money columns are NUMBER(19,4); broker cash_balance is NUMBER(19,2) (inconsistent). Utilization on the server is HALF_UP scale 4 then 2. Amounts reach the client as JSON numbers, formatted by Intl.NumberFormat to 2 places.
  • Dates: all LocalDate; the anchor day's own transactions are excluded from postAnchorSum (assumed already inside the closing balance). A transaction posted after the cut but dated the same day is dropped until the next anchor. Strongly inferred boundary risk.
  • is_excluded is ignored by the balance queries even though the UI copy says excluded transactions are left out of reporting. See Contradiction registry.
  • Single-account and batch-list paths are proven numerically identical (AccountBalanceEquivalenceTest) and constant-query (AccountQueryCountTest, ≤3 queries for N accounts via native findAccountBalanceBatches).

State, invariants, idempotency

  • Account status is derived: closed_on null → ACTIVE; future → CLOSING; past or today → CLOSED. Computed in Java (Account.getStatus, never called externally), in TypeScript (getAccountStatus), and once in a dropped DB column (V81). Three implementations of one trichotomy, one unreachable.
  • Close requires closedOn ≥ MIN(transaction_date); a non-zero balance only produces a warning string. Reopen re-checks last4 collisions.
  • Card.isOpen() is self-referential; the resolver and reward engine additionally require the cardholder not be effectively closed; the client's CardholderItem uses the shallow definition.
  • Idempotency: create is not idempotent (no key); identifier create is idempotent for the same account and rejected for a different one; close/reopen idempotent in effect; no @Version anywhere, so plain edits are last-write-wins.
  • Create vs update asymmetry: update does not default broker financialPosition, so an omitted field nulls it.

Module

M2Transactions, categories, review, rules, links & merge

Executive summary

The transactions table is FinanceOS's central ledger: every money movement, whether typed by hand, parsed from a Gmail alert, parsed from a statement, or uploaded from a file, becomes one row. Around it sit a many-to-many category taxonomy, an LLM-assisted "auto-tag, then a human confirms" categorization system with saved rules, a review queue that records why a row still needs a look, a read-only relationship graph for transfers, refunds and card payments, a duplicate-merge tool, and bulk card re-attribution. Confirmed

The implicit product thesis, confirmed by the code: ingestion is noisy and provisional; every ingested transaction starts as "needs review" and becomes trusted only when a person, or a rule a person verified, confirms it. Almost every other module (rewards, reports, chat, balances, loans) reads this table, so its invariants (one account per row, unique source message per user, well-formed review state) matter far beyond this package.

Search, running balance and pagination

POST /transactions/search uses TransactionListQueryBuilder with its own 16-field whitelist; filters are ANDed; category and reason use EXISTS subqueries; coveredByStatement is a derived pseudo-field (transaction_date ≤ account.last_statement_date); search ORs a case-insensitive LIKE across description, sourced description, account name and category name. Sort whitelist: date, amount, createdAt, id, always followed by the tie-breakers transaction_date DESC, created_at DESC, id DESC. Page size 50. TransactionListQueryBuilder.java:35-289

balance = COALESCE(opening_balance, 0) + SUM(CASE WHEN type='CREDIT' THEN amount ELSE -amount END) OVER (PARTITION BY account_id ORDER BY transaction_date, created_at, id)

Filters apply to the outer query, so a filtered page still shows true running balances over the account's whole history. Example: +1,000 (Jan 1), −300 (Jan 5), −200 (Jan 10); filtering "amount < 0" still shows 700 and 500. Credit cards, brokers and generic accounts get an opening balance of 0. Confirmed

M5Background jobs

Executive summary

A small DB-backed job queue (jobs, job_artifacts) runs every slow or external-dependent operation off the request thread: statement ingest, Gmail sync, price refresh, rule apply, investment import commit and broker reconcile commit. Requests return 202 {jobId} immediately and the UI polls. The worker is a @Scheduled poller (every 2 s, plus an after-commit "poke") inside the same JVM with two threads; claiming is an atomic conditional UPDATE, cancellation is cooperative, and retry always creates a new job row. Confirmed domain/job/JobWorker.java, JobService.java

State machine

new ──enqueue──► PENDING ──claim (UPDATE … WHERE status='PENDING')──► RUNNING RUNNING ──handler returns──► SUCCEEDED (result JSON stored; artifacts deleted) RUNNING ──handler throws───► FAILED (errorCode = exception class, message ≤ 2000 chars; artifacts kept) RUNNING ──boot sweep───────► FAILED / errorCode INTERRUPTED (JobJanitor on ApplicationReadyEvent) PENDING ──cancel───────────► CANCELLED RUNNING ──cancel flag + handler calls ctx.checkCancelled()──► CANCELLED (cooperative only) FAILED | CANCELLED ──retry──► new PENDING row (attempt 0, cloned payload + artifacts, dedupKey null)

There is no INTERRUPTED status; it is an error code on FAILED. Retrying a STATEMENT_INGEST whose artifacts were purged throws "artifacts expired, please re-upload". succeed, fail and markCancelled do not guard on current status, so an out-of-order cancel racing a success could overwrite SUCCEEDED. Medium, latent
